# 客户使用问题归因智能体设计

## 背景

本项目要开发一个面向海外电商运营的数据分析型智能体。首版聚焦海外电商平台的站内客服消息，覆盖 Amazon、TikTok Shop 以及其他可导出客服会话的平台，帮助运营专员或数据分析专员从单条客服会话中识别客户在使用产品时遇到的问题，并给出可执行的根因判断和后续处理建议。

首版不是实时监控平台，也不是客服自动回复机器人。它的核心价值是把一段客服对话转化成内部可读、可复核、可用于后续改进的分析结论。

## 已确认范围

- 业务场景：海外电商销售运营中的客户使用问题分析。
- 平台范围：海外电商平台通用，Amazon 和 TikTok Shop 作为首批重点样例，同时允许接入其他可导出客服会话的平台。
- 数据来源：平台站内客服消息，首版采用人工上传或粘贴方式接入。
- 数据粒度：单条会话级分析。
- 会话语言：多语言混合输入，系统统一输出中文分析结论。
- 主要用户：数据分析专员和运营专员。
- 输出风格：分析解释优先，像内部分析师一样说明问题、依据、根因和建议动作。
- 上下文限制：首版只看客服对话，不依赖商品标题、说明书、FAQ、页面卖点或历史售后资料。

## 首版目标

首版要让用户上传一段海外电商平台客服会话后，获得一份清晰的单会话分析结果。结果应回答四个问题：

1. 客户在使用产品时遇到了什么问题？
2. 为什么系统这样判断？
3. 更可能的业务原因是什么？
4. 下一步优先应该由谁处理，以及怎么处理？

首版成功标准不是完全替代人工判断，而是稳定帮助运营或分析专员完成初筛、归因和行动建议草拟。

## 非目标

- 不做实时 API 接入。
- 不做自动平台同步。
- 不做批量趋势报表。
- 不做销量、广告或经营指标归因。
- 不做跨会话用户画像。
- 不生成面向客户的客服回复。
- 不承诺判断技术真因，只输出基于会话证据的最可能业务判断。

## 推荐方案

采用“隐式结构化 + 显式解释输出”的方案。

系统内部先完成问题分类、业务原因判断、责任方判断和证据充分性判断，再把这些结构化判断组织成自然语言分析结论。用户看到的是分析师风格的解释，而不是一组生硬标签。这个方案兼顾首版体验和后续扩展：现在可以让专员读得懂、用得上；以后也能基于内部结构化字段扩展到汇总报表、趋势分析和质量追踪。

## 核心流程

### 1. 会话输入

用户通过粘贴文本或上传导出文件输入客服会话。首版允许输入 Amazon、TikTok Shop 以及其他海外电商平台的站内消息文本。系统需要保留原始文本和平台来源，便于后续复核与扩展平台解析模板。

### 2. 会话预处理

系统识别会话语言、平台来源、角色、轮次和上下文完整度。系统需要过滤寒暄、物流查询、纯售前咨询等与“产品使用问题”无关的内容。如果会话中存在多种语言，系统以理解原文为准，并统一用中文输出。

### 3. 客户问题识别

系统从对话中提取客户真正卡住的使用任务，而不是只提取关键词。常见问题包括：

- 安装、开箱或组装问题。
- 功能不会用或设置失败。
- 功能表现未达到预期。
- 产品异常、失灵或疑似质量问题。
- 设备、环境、规格或平台兼容性问题。
- 配件缺失或使用条件不满足。

如果客户描述过于模糊，系统应标记信息不足，并说明需要补问的关键问题。

### 4. 业务原因归因

在只看客服对话的前提下，系统判断更可能的业务原因。首版原因类型包括：

- 说明或引导不清。
- 页面承诺或客户预期与实际体验有落差。
- 客服排障引导不足。
- 产品设计容易误用或学习成本高。
- 疑似产品质量异常。
- 疑似兼容性限制。
- 客户操作错误或前置条件未满足。
- 信息不足，暂无法判断。

系统必须把归因建立在对话证据上。没有证据时不能强行判断。

### 5. 责任方判断

系统把业务原因转换成优先处理角色。首版责任方限定为：

- 运营：页面表达、说明内容、预期管理、FAQ 或购买前信息需要优化。
- 客服培训：客服没有完成有效排障、追问不足、话术机械或未能引导客户提供关键信息。
- 产品：产品本身使用路径复杂、容易误用、功能设计导致客户理解困难。
- 供应链或质量：会话中出现损坏、失灵、批次异常、配件缺失等质量相关信号。

当问题涉及多个角色时，系统可以输出主责任方和次责任方。

### 6. 证据充分性判断

每条分析都需要判断证据强度。首版使用三种表达：

- 较明确：会话中有足够事实支撑判断。
- 倾向于：会话中有明显线索，但仍存在其他可能。
- 信息不足：现有对话无法支持可靠判断，需要补充问题。

### 7. 结果生成

系统输出一段面向内部运营和分析人员的中文结论。结论应包含：

- 客户问题摘要。
- 判断依据。
- 最可能业务原因。
- 优先责任方。
- 建议后续动作。
- 需要补充的信息或风险提示。

## 输出示例

```text
客户主要卡在产品连接/配对失败上。依据是客户提到已经按照说明操作，但设备仍无法连接，并且对话中没有看到客服继续追问设备型号、连接环境或错误提示。

当前更倾向于“说明或引导不清 + 客服排障引导不足”，暂不能直接判断为产品质量问题。建议优先由客服培训侧补充标准排障话术，同时由运营检查说明书或页面 FAQ 是否明确覆盖连接失败场景。

下一步建议客服补问：设备型号、系统版本、连接方式、错误提示截图、是否首次使用。如果类似问题高频出现，再升级给产品或质量团队排查兼容性和硬件异常。
```

## 最小功能模块

### 数据输入模块

支持用户粘贴客服会话文本，或上传平台导出的文本、CSV、Excel 文件。首版重点保证单条会话能被稳定输入和保存。

### 会话解析模块

负责识别语言、平台、角色、轮次、有效内容和上下文完整度。解析失败时应提示用户检查输入格式，而不是继续生成不可靠结论。

### 问题归因引擎

负责识别客户问题、判断业务原因、分配责任方、评估证据强度，并生成内部结构化结果。

### 结果生成模块

负责把结构化判断转换为中文自然语言分析。输出要保持克制，明确区分确定判断、倾向判断和信息不足。

### 结果存档模块

保存原始输入、分析结果、生成时间和人工修正记录，便于后续复核和优化。

### 人工修正能力

首版建议预留人工修正入口。分析专员可以调整问题判断、责任方和备注。修正记录可用于后续优化归因规则和提示词。

## 错误处理与边界案例

- 如果客户只说 “not working” 且没有现象描述，系统应输出信息不足，并建议补问具体使用步骤、设备型号、错误提示和发生时间。
- 如果客户反复表示已按说明操作仍失败，系统可倾向判断为说明引导不足、兼容性限制或疑似产品异常，但不能直接断定质量问题。
- 如果客服只重复安抚或机械回复，没有追问关键信息，系统应指出客服排障引导不足。
- 如果客户情绪强烈但事实信息少，系统应区分情绪强度和问题严重度。
- 如果会话内容更像物流、价格、售前咨询或优惠问题，系统应标记为非产品使用问题。
- 如果存在多种可能原因，系统应输出主判断和备选判断，并说明缺少哪些证据。

## 验证方式

首版验证使用 30 到 50 条真实或脱敏客服会话样本。每条样本由人工标注参考结论，再与系统输出对比。验证重点包括：

- 问题识别是否准确。
- 判断依据是否来自会话内容。
- 业务原因是否合理。
- 责任方分配是否可执行。
- 建议动作是否具体。
- 不确定性表达是否克制。

首版通过标准是：系统能稳定节省分析专员初筛时间，并且不会在证据不足时输出武断结论。

## 后续扩展方向

- 接入商品标题、描述、说明书、FAQ 和页面卖点，提升根因判断准确率。
- 支持批量会话分析，按 SKU、ASIN、店铺、时间段汇总高频问题。
- 增加趋势报表和异常预警。
- 接入客服系统或平台 API，实现半自动或实时同步。
- 引入人工修正反馈闭环，持续优化问题分类和归因规则。

## 开放约束

首版默认使用中文输出分析结论。后续如果团队需要面向海外客服或海外业务负责人输出，可增加英文或多语言报告模式。首版暂不决定具体技术栈，技术方案将在实现计划阶段根据仓库现状、可用依赖和部署方式进一步确定。
