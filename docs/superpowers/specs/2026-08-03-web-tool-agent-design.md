# 网页工具型个人智能体设计文档

**日期：** 2026-08-03

## 1. 目标

构建一个基于 Python 的单用户网页聊天智能体，主要供个人在本机使用。它需要同时具备对话能力、网页搜索能力、本地文件阅读能力和知识库检索能力，并通过统一的网页界面把工具执行过程和最终回答清晰展示出来。

第一版重点是稳定、可控、可扩展，而不是追求高度自动化或复杂工作流。系统应优先支持日常开发辅助、文档查阅、项目理解和资料检索。

## 2. 范围

### 2.1 第一版包含的能力

1. 多轮网页聊天
2. 根据问题需要调用网页搜索工具
3. 读取指定工作目录内的文本文件
4. 上传文档并建立本地知识库索引
5. 基于知识库片段进行检索增强回答
6. 在前端展示本轮工具调用记录
7. 保存会话和消息历史
8. 对工具失败、模型失败、编码异常给出明确错误提示

### 2.2 第一版不包含的能力

1. 多用户账号与权限控制
2. 自动写文件、改代码、执行危险命令
3. 多智能体协作
4. 插件系统或开放式工具市场
5. 大规模网页抓取或高并发搜索
6. 语音、多模态、图片理解
7. 复杂后台任务和长时间异步工作流

## 3. 目标用户与使用方式

### 3.1 目标用户

唯一目标用户是开发者本人。

### 3.2 使用方式

用户通过本地网页聊天页与智能体交互。网页作为统一入口，不要求额外的桌面客户端或命令行交互作为主流程。

## 4. 总体架构

系统分为四层：

### 4.1 Web 前端

负责消息输入、消息展示、工具执行记录展示、错误提示展示和历史会话切换。前端保持轻量，优先复用现有静态页面结构。

### 4.2 FastAPI 后端

负责接收前端请求、维护会话上下文、调用模型、编排工具调用、处理错误并向前端返回结构化结果。后端是系统唯一的业务入口。

### 4.3 工具层

提供可注册、可调度、可追踪的工具能力。第一版包含三类工具：

1. 网页搜索工具
2. 本地文件读取工具
3. 知识库检索工具

### 4.4 存储层

负责保存会话、消息、文档元数据、知识库索引和上传文件。第一版优先使用本地存储方案。

## 5. 技术栈

推荐采用以下技术栈：

- 后端：`Python 3.11+`
- Web 框架：`FastAPI`
- 前端：现有 `HTML + CSS + JavaScript` 轻量静态页面
- 数据库：`SQLite`
- 向量索引：`FAISS`
- 模型接入：现有 `OpenAI-compatible provider`
- 文档存储：本地文件夹

选择这套方案的原因：

1. 当前仓库已经具备 Python 项目骨架和 web/provider/memory 模块
2. 单用户个人场景下，本地存储足够且运维成本最低
3. 可以在不引入重型 Agent 框架的前提下实现清晰的工具型智能体
4. 便于后续按需扩展更复杂的工具和工作流

## 6. 代码结构设计

在现有仓库基础上扩展，保持模块职责清晰。

### 6.1 保留并扩展的模块

- `src/dev_agent/web/`
- `src/dev_agent/providers/`
- `src/dev_agent/memory/`
- `src/dev_agent/tools/`

### 6.2 建议新增的模块

- `src/dev_agent/chat/`
  - 负责对话编排、上下文组装、工具调用决策、回答生成
- `src/dev_agent/storage/`
  - 负责 SQLite 中的会话、消息、文档元数据读写
- `src/dev_agent/knowledge/`
  - 如果后续需要把文档导入和检索逻辑从 `memory/` 中明确拆分，可放在这里

### 6.3 建议的最小文件边界

- `chat/orchestrator.py`
  - 管理单轮对话流程
- `chat/session_service.py`
  - 管理会话与消息持久化
- `tools/registry.py`
  - 统一注册工具、暴露工具元数据
- `tools/web_search.py`
  - 负责搜索和网页正文抓取
- `tools/file_reader.py`
  - 负责安全读取工作目录内文本文件
- `tools/knowledge_search.py`
  - 负责知识库检索
- `storage/sqlite_store.py`
  - 负责 SQLite 访问
- `web/api.py`
  - 暴露聊天、上传、会话等接口

## 7. 关键数据流

用户发起一次提问后的标准流程如下：

1. 前端将用户消息发送到 FastAPI
2. 后端读取当前会话最近几轮消息
3. 编排层判断是否需要调用工具，以及调用哪些工具
4. 如果需要项目上下文，调用文件读取工具
5. 如果需要外部资料，调用网页搜索工具
6. 如果问题与已上传文档相关，调用知识库检索工具
7. 后端把用户问题、会话上下文和工具结果一起发送给模型
8. 模型生成最终回答
9. 前端同时展示最终回答和本轮工具执行记录

这一流程必须保证工具调用记录可见，避免系统表现为完全黑盒。

## 8. 工具能力设计

### 8.1 网页搜索工具

职责：

1. 根据问题进行少量网页搜索
2. 获取少量高相关结果
3. 抓取网页正文
4. 将抓取结果返回给编排层，由模型总结

第一版限制：

1. 单次提问只允许少量搜索请求
2. 不支持批量探测大量站点
3. 不支持循环重试轰炸
4. 不支持深度爬虫

### 8.2 本地文件读取工具

职责：

1. 读取指定白名单目录中的文本文件
2. 返回文件内容或片段，供模型理解项目

第一版限制：

1. 仅支持白名单目录
2. 仅支持文本文件
3. 默认只读
4. 不允许访问任意磁盘路径

### 8.3 知识库检索工具

职责：

1. 接收上传文档
2. 进行文本切分与向量化
3. 建立本地向量索引
4. 在提问时返回相关片段

第一版限制：

1. 仅支持基础导入和检索
2. 不支持多租户知识库空间
3. 不支持复杂权限体系
4. 不支持自动同步大量目录

## 9. 会话与状态管理

第一版需要持久化以下数据：

1. 会话列表
2. 会话消息历史
3. 上传文档元数据
4. 知识库索引位置
5. 工具调用记录

建议策略：

1. 会话和消息保存在 SQLite
2. 上传文档保存在本地目录
3. 向量索引保存在本地索引目录
4. 聊天时只加载最近几轮消息进入上下文，以控制成本

## 10. 前端交互设计

网页聊天页至少需要以下区域：

1. 聊天消息区域
2. 输入框和发送按钮
3. 工具调用记录区域
4. 错误提示区域
5. 历史会话列表

前端交互原则：

1. 最终回答与工具记录分开展示
2. 用户应能明确看到本轮是否进行了搜索、读文件、查知识库
3. 当工具或模型失败时，应展示易懂的错误信息
4. 页面优先轻量、稳定、可维护，而不是过度复杂

## 11. 错误处理策略

### 11.1 模型调用失败

前端展示模型请求失败，并返回具体错误类型，例如超时、认证失败或上游供应商错误。禁止静默吞错。

### 11.2 搜索失败

若搜索失败，应返回搜索工具失败信息，并允许系统根据上下文选择：

1. 明确告知无法完成外部查询
2. 在条件允许时退回为仅基于已有上下文回答

### 11.3 文件读取失败

应明确区分以下错误：

1. 文件不存在
2. 路径不在白名单目录内
3. 文件编码无法安全解析
4. 文件类型不支持

### 11.4 知识库检索失败

应明确提示以下情况：

1. 尚未建立索引
2. 文档未上传
3. 向量化失败
4. 检索服务异常

## 12. 编码与文本处理要求

所有读写文件操作必须优先保证编码一致性，默认目标编码为 `UTF-8`。对于中文内容，禁止使用 `\\uXXXX` 形式替代正常中文字符。

第一版文件读取逻辑应满足：

1. 读取前检测文本编码
2. 优先按 `UTF-8` 处理
3. 必要时兼容常见中文编码，避免乱码
4. 出现不可恢复的编码问题时，返回明确错误，而不是输出损坏文本

## 13. 安全边界

虽然该系统仅供个人使用，但第一版仍需设置明确边界：

1. 文件访问必须限制在配置的白名单目录
2. 默认只开放搜索、读文件、查知识库三类工具
3. 默认不开放写文件、执行 shell、删除文件等高风险能力
4. 上传文档需要限制文件大小、类型和切片数量
5. 搜索调用需要有限流策略，避免触发供应商或代理通道熔断

## 14. Prompt 与模型行为约束

系统提示词应明确约束模型：

1. 只能基于已有上下文和工具返回结果作答
2. 无法获取信息时必须明确说明不知道
3. 不得伪造“已查看文件”“已搜索网页”“已读取知识库”等行为
4. 在需要工具时优先使用工具，而不是凭空补全事实

## 15. 测试策略

第一版至少覆盖以下测试：

### 15.1 单元测试

- 工具注册
- 文件白名单校验
- 文件编码识别
- 会话存储
- 文档切分和检索

### 15.2 接口测试

- 聊天接口
- 文档上传接口
- 会话列表接口
- 会话消息获取接口

### 15.3 前端基础测试

- 消息渲染
- 工具记录展示
- 错误提示展示

### 15.4 集成测试

模拟一次完整流程：

1. 用户提问
2. 系统决定调用一个或多个工具
3. 工具返回结果
4. 模型生成回答
5. 前端成功展示最终结果和工具记录

## 16. 第一版成功标准

若系统满足以下条件，即视为第一版成功：

1. 用户能够在网页里进行多轮连续对话
2. 系统能够根据问题决定是否调用搜索、文件、知识库工具
3. 工具执行过程对用户可见
4. 系统能够稳定读取指定目录下的文本文件
5. 系统能够导入常用文档并完成基础检索问答
6. 出错时能返回明确原因，而不是卡死或误导性回答
7. 系统可以作为日常开发辅助、查资料和读文档的个人助手持续使用

## 17. 后续扩展方向

以下内容可以作为第二版或后续版本规划：

1. 安全写文件能力
2. 可控命令执行能力
3. 更强的网页信息抽取
4. 更复杂的工具编排
5. 多模型路由
6. 更完整的长期记忆
7. 多会话策略优化

## 18. 结论

第一版应以“单用户、本地优先、网页交互、工具可见、默认只读”为核心原则，在当前 Python 项目骨架基础上逐步扩展，而不是重新搭建一套重型架构。

该方案既能较快做出可用产品，又能为后续增加写文件、执行命令和更复杂工作流保留清晰扩展位。
